# GEMM CUDA 优化复盘

## 1. 项目目标

本项目不是单纯实现 GEMM，而是构建一条可解释、可复现、可量化的优化路径：

- 从 `v0` 到 `v5` 逐步演进；
- 每一步都回答三个问题：
  - 上一版有什么问题？
  - 为什么这一步是合理更新？
  - 改完后数据是否支持结论？

## 2. 数学与性能预判

## 2.1 数学定义

```
C[m, n] = Σ_{k=0}^{K-1} A[m, k] × B[k, n]
A ∈ R^{M×K}, B ∈ R^{K×N}, C ∈ R^{M×N}
```

## 2.2 算术强度估算（方阵 N×N）

| 指标 | 公式 | 结果 |
|------|------|------|
| 数据搬运 | `(M*K + K*N + M*N) * 4 bytes` | `12N² bytes` |
| 计算量 | `2*M*N*K FLOPs` | `2N³ FLOPs` |
| 算术强度 | `2N³ / 12N²` | `N/6 FLOP/Byte` |

## 2.3 Roofline 判断

- GPU（项目环境记录）：FP32 峰值约 25 TFLOPS，DRAM 带宽约 448 GB/s  
- ridge point 约 `55 FLOP/Byte`

| N | 算术强度 | 初步判断 |
|---|----------|----------|
| 128 | ~21 | 偏访存受限 |
| 512 | ~85 | 偏计算受限 |
| 1024 | ~170 | 计算受限 |
| 4096 | ~683 | 计算受限 |

这意味着：小规模先看访存效率，大规模重点看 FMA 利用率与调度效率。

## 3. 版本演进（上一版问题 -> 为什么升级 -> 改动）

## 3.1 v0：朴素基线
**文件：** `gemm_v0_naive.cu`

### 问题
- 每线程只算一个 `C` 元素；
- A/B 元素被大量重复从全局内存读取；
- 访存延迟主导，算力几乎吃不满。理论上应该是计算受限的内容，现在在roofline中却处于memory受限状态。可以参考文档中，gemm_v0_roofline.png文件。

### 下一步规划：
- 减少从全局内存的读写次数：v0版本读写次数为2x（MxK + KxN + MxN）。在v1版本中，通过共享内存复用，将读写次数减少为1x（MxK + KxN + MxN）。
- 优化数据加载形势：通过向量化加载，数据对齐，访存对齐等策略，减少数据加载指令数量，提升访存效率。


### 价值
- 给后续优化提供正确性与性能下限。


## 3.2 v1：共享内存分块

**文件：** `gemm_v1.cu`

### v0 的问题

- 重复全局读写导致带宽浪费；
- 数据复用没有落在 on-chip 存储上。

### 为什么升级到 v1

- GEMM 的经典第一步是 tile + 共享内存复用；
- 能直接减少 DRAM 访问次数。

### 关键改动

- 16x16 tile 的共享内存分块；
- 加入 `float4` 和 `__ldg` 优化访存路径。

## 3.3 v2：线程级寄存器分块

**文件：** `gemm_v2.cu`

### v1 的问题

- 数据虽进入共享内存，但线程每次计算复用不够；
- 指令级并行与寄存器复用不足。

### 为什么升级到 v2

- 将“每线程算 1 个输出”升级为“每线程算一个小块（TMxTN）”；
- 增加每次加载参与计算的次数，提升计算强度。

### 关键改动

- 线程级寄存器 tile（`TM=8, TN=8`）；
- 共享内存 + 寄存器协同复用。

## 3.4 v3：寄存器预取/软件流水

**文件：** `gemm_v3.cu`

### v2 的问题

- 计算与加载串行化程度仍高；
- 对全局内存延迟隐藏不足。

### 为什么升级到 v3

- 软件流水把“加载下一块”和“计算当前块”重叠；
- 目标是降低等待内存返回造成的停顿。

### 关键改动

- 寄存器预取下一 tile；
- 减少纯等待周期，提升流水重叠。

## 3.5 v4：更大 CTA 分块

**文件：** `gemm_v4.cu`

### v3 的问题

- 在更大矩阵上，block 级复用深度仍不够；
- 调度与数据复用粒度需要放大。

### 为什么升级到 v4

- 增大 CTA tile，提升块内数据复用与吞吐；
- 面向大矩阵场景优化。

## 3.6 v5：WMMA（当前为 FP16 输入 + FP32 累加）

**文件：** `gemm_v5.cu`

### v4 的问题

- 仍以传统 CUDA Core 路径为主，算力密度受限；
- 需要进一步探索 Tensor Core 路线。

### 为什么升级到 v5

- 在支持场景下，WMMA 路径通常有更高吞吐上限。

### 关键说明

- 当前版本为 `FP16 input + FP32 accumulate` 的 WMMA 路径；
- 这版在多数规模优于 v4，但不是所有规模都单调更优（见 4096 结果）。

## 3.7 cuBLAS 参考

**文件：** `gemm_cublas_ref.cu`

- `cublasSgemm` 作为工业基线；
- 用于评估自研内核与成熟库的差距。

## 5. 结果解读（面试可直接讲）

1. **v0 -> v3 主线有效**：通过分块、寄存器复用、预取，吞吐显著提升；  
2. **v4/v5 在大矩阵明显优于 v0~v3**：说明大 tile / WMMA 方向正确；  
3. **v5 非全场景单调优于 v4**：2048 上更快，但 4096 上 v4 反超，说明参数和调度仍需按规模调优；  
4. **与 cuBLAS 差距仍在**：尤其 4096 下差距明显，工业库在 kernel 选择、pipeline 深度、调度策略上更成熟。
