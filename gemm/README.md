# GEMM CUDA 优化复盘

本文档描述 `gemm/` 下各版本内核的设计与结论；**命令与路径默认 Ubuntu 22.04 + CUDA 13.2**（可执行文件在 `build/bin/`）。顶层构建步骤见仓库根目录 [`README.md`](../README.md)。

---

## 1. 项目目标

本项目不是单纯实现 GEMM，而是构建一条可解释、可复现、可量化的优化路径：

- 从 **v0** 到 **v4** 逐步演进（中间含 **v3** 双缓冲）；
- 每一步都回答三个问题：上一版有什么问题？为什么这一步合理？数据是否支持结论？

### 1.1 源码与可执行文件（`gemm/CMakeLists.txt`）

| 目标 | 源文件 | 说明 |
|------|--------|------|
| `gemm_v0` | `gemm_v0.cu` | 朴素基线，每线程一个输出元素 |
| `gemm_v1` | `gemm_v1.cu` | 共享内存 16x16 tile，`float4` / `__ldg` |
| `gemm_v2` | `gemm_v2.cu` | 线程级寄存器分块，每线程 **8x8** 子块，块覆盖 128x128 |
| `gemm_v3` | `gemm_v3.cu` | FP32：每线程 **8x4** 子块，`TileK=32`，`cp.async` + 双缓冲 SMEM |
| `gemm_v4` | `gemm_v4.cu` | FP32：在 v3 几何与流水基础上的独立优化版本（`cp.async` + 双缓冲） |
| `gemm_cublas_ref` | `gemm_cublas_ref.cu` | `cublasSgemm`（FP32 输入 + FP32 累加）参考实现 |

单独跑某版本或 cuBLAS 参考：

```bash
./build/bin/gemm_v4
./build/bin/gemm_cublas_ref
```

## 2. 数学与性能预判

### 2.1 数学定义

```
C[m, n] = Σ_{k=0}^{K-1} A[m, k] * B[k, n]
A ∈ R^{MxK}, B ∈ R^{KxN}, C ∈ R^{MxN}
```

### 2.2 算术强度估算（方阵 NxN）

| 指标 | 公式 | 结果 |
|------|------|------|
| 数据搬运 | `(M*K + K*N + M*N) * 4 bytes` | `12N^2 bytes` |
| 计算量 | `2*M*N*K FLOPs` | `2N^3 FLOPs` |
| 算术强度 | `2N^3 / 12N^2` | `N/6 FLOP/Byte` |

### 2.3 Roofline 判断

- GPU（项目环境记录）：RTX 5060 Ti (sm_120)，FP32 峰值约 25 TFLOPS，Tensor Core FP16 峰值更高；DRAM 带宽约 448 GB/s。

| N | 算术强度 | 初步判断 |
|---|----------|----------|
| 128 | ~21 | 偏访存受限 |
| 512 | ~85 | 偏计算受限 |
| 1024 | ~170 | 计算受限 |
| 4096 | ~683 | 计算受限 |

小规模先看访存与 launch 效率，大规模重点看分块策略、流水深度与占用率。

## 3. 版本演进

### 3.1 v0：朴素基线

**文件：** `gemm_v0.cu`

- 每线程只算一个 `C` 元素；A/B 被大量重复从全局内存读取。
- 访存与并行度往往主导，算力难以吃满。

**价值：** 正确性下限与后续加速比的参照。

### 3.2 v1：共享内存分块

**文件：** `gemm_v1.cu`

- 16x16 线程块对应的 tile；在 SMEM 中复用 A/B 条带。
- `float4`、`__ldg` 等减轻全局访问与指令条数。

### 3.3 v2：线程级寄存器分块

**文件：** `gemm_v2.cu`

- 每线程计算 **TMxTN = 8x8** 输出子块；16x16 线程 → CTA 覆盖 **128x128**。
- `kTileK = 16`；`As[kBlockM][kTileK]`、`Bs[kTileK][kBlockN]` 与寄存器累加器协同。

### 3.4 v3：双缓冲共享内存

**文件：** `gemm_v3.cu`

- 在 v2 基础上改为 **每线程 8x4 子块**、`TileK=32`，并保持 CTA `128x128`。
- A/B 共享内存采用双缓冲并结合 `cp.async`，把下一轮 tile 预取与当前轮计算重叠。
- 面向 FP32 口径，当前实现在 4096^3 上可稳定跑到 ~13 TFLOPS 量级。

### 3.5 v4：FP32 独立优化版本

**文件：** `gemm_v4.cu`

- 与 v3 保持同口径（FP32 输入 / FP32 计算 / FP32 输出），避免混合精度对比偏差。
- 保留 `cp.async` + 双缓冲主线，在参数与写回路径上做独立调优。
- 目标不是“引入新数据类型”，而是验证在同精度下的工程优化上限。

### 3.6 cuBLAS 参考（FP32）

**文件：** `gemm_cublas_ref.cu`

- 使用 `cublasSgemm` 作为 FP32 基线实现。
- 与 v0-v4 在精度口径上保持一致，便于直接比较耗时与吞吐。

## 5. 结果解读

1. **口径已统一**：当前 `v0`-`v4` 与 `cuBLAS` 都是 FP32，结果可直接横向比较。
2. **小矩阵（128）时库调用开销明显**：`cuBLAS` 反而慢于自研 kernel；此区间不代表大规模上限。
3. **中大矩阵（256~4096）总体上 cuBLAS 更优**：尤其 1024、4096 上优势明显。
4. **v3/v4 是当前自研最强组**：在 512 规模，`v3` 已接近并略优于 cuBLAS；更大规模仍有 20%~30% 左右差距。
5. **优化方向仍集中在占用率与流水深度**：当前表现符合“分块 + 双缓冲有效，但尚未达到库级调度/内核族选择能力”。
