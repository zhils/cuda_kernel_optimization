# RMSNorm CUDA 优化复盘（面试版）

## 1. 问题背景与目标

RMSNorm 是大模型中非常高频的归一化算子，计算定义如下：

```
y = x / sqrt(mean(x^2) + eps) * gamma
mean(x^2) = (1 / C) * sum_{i=0}^{C-1}(x_i^2)
```

本项目的核心目标不是“功能可用”，而是“性能可解释、优化路径可复现”：

- 给出从 `V0` 到 `V3` 的逐步优化链路；
- 每一步都说明“上一版问题是什么、为什么这么改”；
- 通过实测数据（ms/GFLOPS/相对 CUB 比率）证明优化有效或无效；
- 形成可用于面试讲解的完整材料。

---

## 2. 理论判断：为什么先盯访存

### 2.1 算术强度估算

| 指标 | 估算公式 | 量级 |
|------|----------|------|
| 数据搬运 | 读 `x` + 读 `gamma` + 写 `y` | `~12RC bytes` |
| 计算量 | 平方和 + 归一化缩放 | `~4RC FLOPs` |
| 算术强度 | `4RC / 12RC` | `~0.33 FLOP/Byte` |

结论：算术强度低，属于典型 memory-bound 算子。  
因此优化主线应该是：

- 减少全局内存往返；
- 提升访存并行度与访存形式（向量化、对齐）；
- 降低归约开销与同步开销。

## 3. 版本演进：上一版问题 -> 本版改动 -> 结果

## 3.1 V0（Naive）

**文件：** `rmsnorm_v0_naive.cu`

### 上一版问题（基线本身）

- 每行单线程串行完成平方和与写回；
- 行内并行度几乎没有，SM 利用率低；
- 对 `x` 的读取复用差，吞吐受限。

### 当前实现

- 作为正确性和性能基准，不做复杂优化。

### 面试可讲要点

- V0 的价值是“建立可验证下限”，不是追求高性能；
- 后续所有优化都要证明“比 V0 快，且保持正确”。

## 3.2 V1（减少全局访存 + 访存形式优化）

**文件：** `rmsnorm_v1.cu`

### V0 的主要问题

- `x` 访问有重复；
- 归约和写回阶段没有充分利用 block 内协同；
- 全局访存事务数偏高。

### 为什么升级到 V1

- RMSNorm 的核心是 memory-bound，先优化访存收益最大；
- 先做“低风险高收益”改动（共享缓存、只读路径、向量加载）。

### V1 的关键改动

- 可暂存时把一行 `x` 放进共享内存，减少重复全局读；
- 大列数走 stream 路径 + block 内树形归约；
- 使用 `__ldg` 和 `float4` 条件向量化。

### 结果

- 小中尺寸收益明显，是后续版本的基础。

## 3.3 V2（向量化 + Warp 归约）

**文件：** `rmsnorm_v2.cu`

### V1 仍存在的问题

- 归约和写回阶段仍有优化空间；
- 访存指令数仍可进一步压缩；
- 对大 hidden dim 的吞吐还有上限。

### 为什么升级到 V2

- 在 memory-bound 算子里，访存指令条数和并发度直接影响速度；
- Warp 级归约通常比纯共享内存树归约更轻量。

### V2 的关键改动

- `float4` 更系统化用于 load/store 与局部累加；
- 用 warp + shared 协同做跨 warp 归约；
- 减少不必要的同步与中间写回。

### 结果

- 在 `1024x1024` 这类中大规模上表现最好（单核版本中）。

## 3.4 V3（融合路径）

**文件：** `rmsnorm_v3.cu`

### V2 的问题

- V2 并非在所有尺寸都最优；
- 某些规模下归约与写回阶段仍有调度效率损失。

### 为什么升级到 V3

- 尝试通过更“融合”的执行路径，减少阶段切换开销；
- 提升全线程参与度，优化大尺寸吞吐。

### V3 的关键改动

- 尽量让归约/输出阶段持续高并行；
- 使用更带宽友好的访问路径；
- 保留数值稳定相关处理。

### 结果

- `512x512` 上优于 V2；
- 但在 `1024x1024`、`4096x4096` 上 V2 仍略优，说明 V3 不是“绝对替代”，而是“特定规模更优”。

## 4. 与 CUB 的对比（重点）

## 4.1 执行时间（ms）

> 数据来源：`data/results/rmsnorm_all_comparison.csv`

| 矩阵规模 | v0 | v1 | v2 | v3 | CUB |
|----------|-------|------------|------------|-----|
| 128×128 | 0.0317 | 0.0212 | 0.0178 | 0.0047 | 0.0857 |
| 256×256 | 0.0870 | 0.0189 | 0.0176 | 0.0089 | 0.0339 |
| 512×512 | 0.1694 | 0.0314 | 0.0230 | 0.0074 | 0.0170 |
| 1024×1024 | 0.3317 | 0.0890 | 0.0544 | 0.0111 | 0.0519 |
| 4096×4096 | 1.3633 | 1.2899 | 0.6193 | 0.3892 | 0.4704 |

## 4.2 吞吐量（GFLOPS）

> 按 `~4RC FLOPs` 估算，由上述 ms 换算得到

| 矩阵规模 | v0 | v1 | v2 | v3 | CUB |
|----------|-------|------------|------------|-----|
| 128×128 | 2.07 | 3.09 | 3.69 | 13.95 | 0.76 |
| 256×256 | 3.01 | 13.88 | 14.87 | 29.50 | 7.74 |
| 512×512 | 6.19 | 33.36 | 45.55 | 142.55 | 61.59 |
| 1024×1024 | 12.65 | 47.14 | 77.12 | 378.72 | 80.86 |
| 4096×4096 | 49.23 | 52.03 | 108.37 | 172.46 | 142.66 |

## 4.3 相对 CUB 性能比率

| 矩阵规模 | v0/CUB | v1/CUB | v2/CUB | v3/CUB |
|----------|--------|--------|--------|--------|
| 128×128 | 2.71x | 4.04x | 4.83x | 18.38x |
| 256×256 | 0.39x | 1.79x | 1.92x | 3.81x |
| 512×512 | 0.10x | 0.54x | 0.74x | 2.31x |
| 1024×1024 | 0.16x | 0.58x | 0.95x | 4.68x |
| 4096×4096 | 0.35x | 0.36x | 0.76x | 1.21x |

### 结果解读（面试可直接讲）

- 小尺寸（128/256）：`v3` 与 `v2` 明显领先 CUB，说明库路径存在固定启动开销；
- 中尺寸（512/1024）：`v3` 继续保持领先，`v2` 与 CUB 接近；
- 大尺寸（4096）：`v3` 仍领先 CUB（约 1.21x），`v2` 略低于 CUB；
- 结论是：在当前实现与测试设置下，`v3` 是对 CUB 最有竞争力的版本。

## 5. 从“上个版本文档”到“当前版本文档”的改进点

上一版 README 的主要问题：

- 有结果，但“为什么要这样优化”解释不够成体系；
- 缺少“上一版问题 -> 当前版改动”的因果链；
- 指标有时间数据，但面试常问的吞吐量、相对库性能比率不完整；
- 结论偏描述性，缺少“按规模分段”的可解释结论。

当前版本的改进：

- 按优化工程思路重写：背景 -> 理论 -> 演进 -> 对比 -> 结论；
- 每个版本都明确写了“上一版问题”和“升级理由”；
- 增加了与 CUB 的三维对比（ms/GFLOPS/ratio）；
- 增加 Nsight 占位标记，便于后续补图形成完整证据链。
