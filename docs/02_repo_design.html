一、设计原则

核心原则

面试官打开你的 GitHub 链接，30 秒内需要看到：
"这个人能写高性能 CUDA kernel，懂得分析和优化"，
而不是 "这个人收集了很多学习笔记"。

二、文件去留决策

对原仓库中的每个目录/文件做出明确的 保留 或 不放入 决策：

现有目录/文件 决定 理由
common/ 保留 公共工具库 (benchmark, cuda_utils)，所有算子都依赖
operators/06_matmul/gemm/ 重构后保留 GEMM 是最核心的算子，已有多个优化版本，重构命名后展示
operators/09_softmax/softmax/ 重构后保留 Softmax 面试高频考点，有 online / warp shuffle 等优化空间
operators/03_normalization/rmsnorm/ 重构后保留 LLM 核心算子，展示 warp reduce / vectorized load 等技巧
docs/benchmark_environment.md 保留 硬件/软件环境说明，benchmark 结果的可信度基础
operators/ 其余所有算子
01_elementwise, 02_reduce, 04_activation,
05_embedding, 07_attention, 08_conv, 10_scan, ...		 不放入 全是 naive 实现，没有渐进优化。数量多反而稀释质量，给人"只会写基础版"的印象
cuda_hardware_learning/ 不放入 学习笔记，不是工程产出
cuda_optimization_knowledge/ 不放入 学习笔记，知识应该体现在代码和 README 的分析中
cuda_sass_learning/ 不放入 SASS 学习资料，不属于展示内容
cuda_performance_analysis/ 不放入 分析过程可以融入各算子的 README 中
tensorrt_learning/ 不放入 TensorRT 学习资料，与 CUDA kernel 优化主题不符
optimization_strategies/ 不放入 优化策略笔记 → 应体现在代码注释和文档中
optimization_benchmarks/ 不放入 旧 benchmark，重构后需要重新生成
scripts/ 不放入 辅助脚本，不是核心展示内容
data/, profiles/ 不放入 运行产物 / profiling 数据，应在 .gitignore 中排除
include/, src/ 不放入 旧练习代码，已合并到 common/ 中
OPERATORS_INDEX.md 不放入 60+ 算子的索引表，展示仓库只有 3 个算子不需要
PROJECT_OVERVIEW.md 不放入 旧项目概览，展示仓库需要全新的 README
决策总结

保留 5 个部分：common/ + 3 个重点算子 + benchmark_environment.md
不放入 15+ 个部分：所有学习笔记、naive 算子、脚本、数据文件
原则：宁少勿多，每一个文件都应该展示你的工程能力

三、目标目录结构

重构后的仓库目录清晰、扁平，每个算子都是独立的子项目：

cuda-kernel-optimization/ ├── README.md ← 最重要的文件 ├── CMakeLists.txt ├── .gitignore │ ├── common/ ← 公共工具库 │ ├── CMakeLists.txt │ ├── include/common/benchmark.h, cuda_utils.h │ └── src/benchmark.cpp │ ├── gemm/ ← GEMM: 渐进优化 │ ├── README.md │ ├── gemm_v0_naive.cu │ ├── gemm_v1_tiled_smem.cu │ ├── gemm_v2_bank_conflict_free.cu │ ├── gemm_v3_thread_tiling.cu │ ├── gemm_cublas_ref.cu │ └── benchmark_all.cu │ ├── softmax/ ← Softmax: 渐进优化 │ ├── README.md │ ├── softmax_v0_naive.cu │ ├── softmax_v1_shared_mem.cu │ ├── softmax_v2_online.cu │ ├── softmax_v3_warp_shuffle.cu │ ├── softmax_cudnn_ref.cu │ └── benchmark_all.cu │ ├── rmsnorm/ ← RMSNorm: 渐进优化 │ ├── README.md │ ├── rmsnorm_v0_naive.cu │ ├── rmsnorm_v1_warp_reduce.cu │ ├── rmsnorm_v2_vectorized.cu │ ├── rmsnorm_v3_fused.cu │ └── benchmark_all.cu │ └── docs/ └── benchmark_environment.md
结构亮点

扁平化：gemm/ softmax/ rmsnorm/ 直接在根目录下，不需要 operators/06_matmul/gemm 这样的深层嵌套
版本递进：v0 → v1 → v2 → v3 文件名清晰表达优化路径
参考对比：每个算子包含 cublas/cudnn 参考实现 + 统一 benchmark
总文件数：约 31 个，每个文件都有存在的理由

四、文件命名规范

文件名应该一眼看出优化手段，而不是毫无意义的数字编号：

原文件名 新文件名 优化手段
gemm.cu → gemm_v0_naive.cu 基础实现
gemm1.cu → gemm_v1_tiled_smem.cu Shared Memory Tiling
gemm2.cu → gemm_v2_bank_conflict_free.cu 消除 Bank Conflict
gemm3.cu → gemm_v3_thread_tiling.cu Thread-level Tiling
nvidia_ref.cu → gemm_cublas_ref.cu cuBLAS 参考实现
gemm_all_benchmark.cu → benchmark_all.cu 统一性能对比
命名原则

格式：{算子}_v{N}_{优化手段}.cu
版本号：v0 = naive → v1 → v2 → v3 递进
优化手段：用英文关键词描述核心优化 (tiled_smem, bank_conflict_free, warp_shuffle, ...)
参考实现：{算子}_{库名}_ref.cu (如 gemm_cublas_ref.cu, softmax_cudnn_ref.cu)

五、README 设计模板

5.1 顶层 README 结构

顶层 README.md 是面试官的第一入口，需要在 30 秒内传达核心信息：

1
项目标题 + 一句话介绍
"从 naive 到高性能的 CUDA kernel 渐进优化实践，包含 GEMM / Softmax / RMSNorm 三个核心算子"
2
性能总览表格 (最吸引眼球)
一个表格展示每个算子的 "naive → 最终优化版 → 库参考" 的性能数据
例如：GEMM v3 达到 cuBLAS 的 85%
3
项目结构 (快速导航)
简洁的目录树 + 每个子目录的一句话说明
4
编译 & 运行方式
3 行命令搞定：mkdir build && cd build && cmake .. && make
5
硬件环境
GPU 型号 / CUDA 版本 / 驱动版本 — 链接到 docs/benchmark_environment.md

5.2 单算子 README 模板 (7 要素)

每个算子目录中的 README.md 是展示深度的关键，应包含以下 7 个要素：

1
算法原理
数学公式 + 一句话说清楚这个算子在做什么
2
优化路径
v0 → v1 → v2 → v3 每一步优化了什么，为什么
3
性能对比表
各版本 vs 库参考的 GFLOPS / 带宽利用率 / 加速比
4
核心代码片段
每个版本的关键优化代码（不是全部代码，只是 diff）
5
Profiling 分析
nsight 截图 / metrics 数据解读：瓶颈在哪，如何解决
6
已知局限 & 改进方向
坦诚说明还有什么没做、可以继续优化的方向
7
参考资料
论文 / 博客 / 官方文档链接，展示学习深度
README 写作建议

重点在分析而非罗列：不要只贴 benchmark 数字，要解释为什么 v2 比 v1 快了 3x
配图优于纯文字：内存访问模式、tiling 示意图、profiling 截图都是加分项
适当使用 LaTeX：GitHub 已支持数学公式，用 $O(N^2)$ 而不是 O(N^2)

六、对比：重构前后

维度 原仓库 展示仓库
